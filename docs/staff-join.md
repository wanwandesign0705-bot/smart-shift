# スタッフの参加（作業5）

## 流れ

```
店長：設定 → 「スタッフの参加」→ スタッフの行の「招待リンクを発行」
  → 出てきたリンク（または QR コード）を、LINE などで本人に送る
スタッフ：リンクを開く → 「参加する」（ロボット対策の確認のあと）
  → その端末で、公開されたシフト・自分の給与見込・有給の残りが見られる
```

- メールアドレスもパスワードもいりません。裏では Supabase の「匿名ログイン」で、その端末を名簿の1行に結びつけています
- 次からは、同じ端末・同じブラウザで開くだけで見られます
- 店長の画面では、スタッフごとに「参加済み／招待中／未招待」が出ます

## 守り

| こと | しくみ |
|---|---|
| リンクの推測 | トークンは48文字のランダムな英数字。データベースには暗号化した形（SHA-256）だけを保存 |
| リンクの使い回し | 1回だけ使え、7日で使えなくなる。再発行すると、前のリンクは使えなくなる |
| リンクが記録に残る | トークンは URL の「#」のあと（`#invite=…`）に置く。「#」のあとはサーバーに送られず、アクセスの記録に残らない。参加したらアドレスから消す |
| ロボットによる大量参加 | 匿名ログインの前に Turnstile の確認 |
| スタッフから見えるもの | **自分の**公開済みのシフト、**自分の**名簿の1行、シフト区分、自分の時給（`my_wage` 関数）、自分の申請と交代の募集中のものだけ。ほかの人の名簿・シフト・時給・申請・予算は、データベースが返さない（`003_staff_privacy.sql`） |
| 参加していない端末 | Supabase を使う版では、名前を選んで見る画面を出さない。参加していない人や、店長がロックした端末には「招待リンクを開いてください」の案内だけを出す |
| 機種変更・紛失 | 店長が再発行すると、新しい端末が結びつき、前の端末は見られなくなる。「参加を解除」でも外せる |
| 店長の端末でリンクを開く | 店長のアカウントがスタッフに結びつかないよう、参加させない |
| スタッフの端末に残るもの | この端末の保存（localStorage）には、お店の名簿や時給を書かない |

## 設計書から変えたこと

設計書では、リンクを確かめる係として Edge Function「redeem-invite」を置く予定でした。データベースの関数 `redeem_invite`（作業2の schema.sql に入っている）が同じことをし、トークンの長さ・1回限り・期限・ロボット対策で十分に守れるため、Edge Function は置いていません。Supabase に置くプログラムが1つ減り、運営の手間も減ります。

## 公開後に見つかって直したこと（2026-11-27）

店長の確認で、スタッフ画面からほかの人のシフトと給与見込が見えることが分かりました。原因は3つでした。

1. v2.3 の「名前を選ぶ欄」が残っていて、参加していない端末や、店長がロックした端末で、だれの名前でも選べた
2. 「全体のシフト」タブで、ほかの人のシフトが見えた
3. データベースの守りが広すぎ、スタッフが同じお店の全員の名簿（入社日・扶養・学生など）・公開済みシフト・申請（理由を含む）を読めた

直し方：データベースで、スタッフが読めるのを本人の分だけにした（`003_staff_privacy.sql`）。画面では名前を選ぶ欄と「全体のシフト」をなくし、参加していない端末には案内だけを出す。テストに「ほかの人の名簿・シフト・申請を読めない」「参加していない端末・ロックした端末で給与見込が出ない」を足した。

## データベースの追加（`supabase/migrations/002_staff_self.sql`、`003_staff_privacy.sql`）

- `002`：スタッフが自分の時給だけを読むための関数 `my_wage`
- `003`：スタッフが読める範囲を、本人の分だけに狭める

新しく作るときは `schema.sql` に入っています。すでに作った Supabase には、`002` → `003` の順に SQL エディタで流します（どちらも2回流しても大丈夫です）。

## まだできないこと（作業6で）
