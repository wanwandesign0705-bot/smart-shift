# 管理画面のデータを Supabase に保存する（作業4）

## 変わったこと

店長がログインしてお店を開いている間は、管理画面の操作が Supabase に保存されます。別のパソコンやスマホでログインしても、同じシフト・名簿・設定が出ます。

| 画面上部の表示 | 意味 |
|---|---|
| 保存済み | Supabase に保存されている |
| 保存中… | 送っている途中（操作のあと0.6秒待ってから、まとめて送る） |
| 保存できません | 送れなかった。理由が画面下に出る。次の操作のときに、もう一度送る |

送っていない変更があるときにページを閉じようとすると、確認が出ます。

ログアウトすると、画面からお店のデータが消えます。この端末（ブラウザ）には、お店の名簿や時給を残しません。

## Supabase に保存するもの

| 画面の項目 | Supabase の表 |
|---|---|
| 業種、会社全体の従業員数、希望休・有給の締切日 | `stores` |
| 作成期間、必要人数、繁忙加算、巡回パターン、予算、連勤上限・勤務間インターバル | `store_settings` |
| シフト区分（時間帯・色・最低人数・休憩・明け休み） | `shift_types` |
| 名簿（名前・役割・勤務形態・固定曜日・入社日・所定日数・扶養・学生など） | `staff` |
| 時給 | `staff_private`（スタッフからは読めない） |
| 1人1日のシフト、有給（全日・半日）、希望休、メモ | `shift_assignments` |
| 公開した期間 | `shift_publications`（スタッフはこの期間のシフトだけ読める） |

## しくみ（開発者向け）

- 画面は今までどおり `save()` を呼ぶだけ。`src/data.js` が S（画面の状態）を表の行に変え（`storeToRows`）、前回送った行と比べて（`diffRows`）、変わった行だけを送る
- 送る順番は「消す（シフト → 時給 → 名簿 → 区分）→ 足す・直す（区分 → 名簿 → 時給 → シフト）→ 設定 → 公開」。スタッフの上限を超えないよう、消すほうを先にする
- 画面で新しく作った区分・スタッフの仮の ID（`s0`、`t` + 時刻）は、送る前に UUID に付け替える（`normalizeIds`）
- 読み込みは1000行ずつ（Supabase は1回に最大1000行しか返さないため）

## テスト（2026-11-26）

| コマンド | 確かめること | 結果 |
|---|---|---|
| `npm run test:cloud` | 管理画面の操作が保存され、開き直しても残るか。送る量が最小か。1000行を超える読み込み、テンプレートの切り替え、保存の失敗と送り直し、ログアウト後に端末に残らないか | 31項目すべて合格 |
| `bash tests/run-cloud-rows-test.sh` | アプリが送る操作が、schema.sql の DB に店長の権限で通るか。スタッフからは公開した期間だけ見え、時給は見えないか | 11項目すべて合格 |
| `npm run test:account` | 作業3の流れ（お店を作った直後のシフトの保存も含む） | 34項目すべて合格 |
| `npm run test:schema` ／ `bash tests/run-template-test.sh` | DB の守り／業種テンプレート | 66項目／8業種すべて合格 |

`test:cloud` は、本物の Supabase の代わりに `tests/fake-supabase.cjs`（送られた行を覚えておく偽物）を使います。守り（RLS）は偽物では確かめず、`run-cloud-rows-test.sh` で本物と同じ DB を使って確かめます。

### テスト中に見つけたこと
- **（直した不具合）** 作業3で説明のコメントを足したとき、同じ行にあった「ロック画面では上の帯を隠す」処理まで、コメントの一部として消していた。ロック画面が全体を覆うので見た目は同じで、画像の比較では見つからなかった。比較スクリプトに「画面の中身（HTML）も比べる」を足したことで見つけ、直した
- テスト用の偽物が、スタッフの「在籍中」の初期値を真似していなかったため、作ったばかりのスタッフを読み込めていなかった（アプリではなく偽物の不具合。本物の DB と同じ動きに直した）
- 消したスタッフの古いシフトが、画面の側にだけ残ることがある。保存はされず、開き直すと消える（害はない）
